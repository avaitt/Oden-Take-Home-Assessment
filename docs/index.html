Write-up¶

The problem¶

Unplanned breakdowns are expensive. When a part fails on a production line (a breakdown), the line stops, the crew scrambles for a spare part, and output is lost. If you could see a breakdown coming a day early, you could plan the repair instead of reacting to it.

The task. Oden's brief: take a year of machine data and find precursors, patterns in the data that show up before a failure. Each one has to be written as a simple yes/no rule checked every hour ("alarm" or "no alarm"), so an operator can understand it and trust it. Keep up to three.

How a rule is judged. The brief asks for three numbers:

  • Lift: how much more often the rule fires before failures than in normal running.
  • Precision: of the alarms it raises, how many are followed by a real failure.
  • Coverage: of the failures, how many it warned about in time.

To rank rules I fold precision and coverage into one score, F1 (0 to 1), which is high only when both are high (section 5.1).

"In time" means inside a set window of hours before the failure, early enough to act (H and W, section 5.2).

What makes it hard. Failures are rare, and sensors wobble all the time. A rule that fires constantly catches every failure, but nobody trusts it. A rule that rarely fires is usually right, but misses most failures. And when many ideas are tried, some will look good by luck, or by quietly using information from the future. The job is to find rules that are genuinely useful, and prove it on machines they have never seen. So I split the 100 machines in half: 50 training machines to build the rules on, and 50 test machines kept aside, used only to grade them at the end. Every score on this page comes from the test machines (section 3).

Why it matters for Oden. This is a small version of Oden's own Agentic Root Cause Analysis workflow: understand the operation, narrow the search, come up with ideas, test them fairly, and turn the winners into alarms (section 8).

1 · Shortlist: the warning signs that made the cut¶

Brief: your shortlist of surviving precursors.

The story in plain words. Each machine has four parts (comp1–comp4). Each part has one sensor that watches it and one error code it can log. About two days before a part breaks, its sensor moves off its normal level and stays there. About one day before, that part's own error code shows up.

The catch: sensors also move off for no reason, about 470 times a year per part, and then settle back. Think of a fever: most pass on their own. The error code is what tells you which fever is serious.

Why the error code matters¶

A drift is a sensor running a fever: clearly off that machine's normal, and staying there for at least a day. The chart counts every drift in 2015. Blue ones were followed by a failure (real); grey ones settled back on their own (look-alikes).

What the chart shows: a drift alone can't be trusted, but a drift with an error code usually can. On the sensor alone, only about 1 in 4 drifts is real. Requiring an error code throws out most look-alikes and keeps almost every real drift, so about 7 in 10 are real.

The ten ideas I tested. Seven are the obvious ones anyone would try first (C01–C07). Three combine clues, based on what the data showed (C08–C10):

C01 Voltage creeps up a machine's voltage rises well above its normal level (an electrical fault) rejected
C02 Rotation sags rotation speed drops well below its normal level (friction or wear) rejected
C03 Pressure builds pressure rises well above its normal level (a blockage) rejected
C04 Vibration rises vibration rises well above its normal level (bearing wear) rejected
C05 Any signal drifts any of the four sensors moves well past its normal level rejected
C06 Any error code the machine logs any error code rejected
C07 Overdue maintenance a part has gone much longer than usual since its last replacement rejected (failed a check)
C08 Drift + any error any sensor reads off and any error code was logged recently kept

Each part has its own sensor and its own error code (comp1 voltage · error1, comp2 rotation · error2/3, comp3 pressure · error4, comp4 vibration · error5), so C09 is really four small rules, one per part, each asking "is this part's sensor off and did this part's code fire?"

2 · Rejected candidates, and why¶

Brief: the candidates you rejected and why.

Each of the ten ideas from section 1 was tried with several settings (how strict the line is, how far back to look, and so on) and its best setting kept (appendix C.2). Then each idea had to pass four checks before it could compete:

  1. Not luck: it must clearly beat scrambled copies of itself (same number of alarms, shifted randomly in time). Rules built from pure random noise score about 0.08 out of 1; C09 scores 0.94.
  2. It fires more before breakdowns than in normal running, at least twice as often (lift ≥ 2).
  3. It catches a meaningful share of breakdowns, at least 5% (coverage ≥ 5%).
  4. No peeking at the future: set up on January–June only, it must still work on July–December.

Nine of the ten passed, and the top three by score were kept. Why the other seven lost:

  • Watching one sensor at a time (C01–C04): real signals, but fooled by the false "fevers". Only about 1 in 4 alarms is real.
  • Watching all four sensors at once (C05): catches 98% of breakdowns, but nearly 3 in 4 alarms are false. A crew would learn to ignore it.
  • Alarming on any error code (C06): misses about half of all breakdowns.
  • Alarming when a part is overdue for service (C07): the only idea that failed a check. It looked good only because it was quietly using information from the future; with past data alone it caught nothing (appendix C.5).

2.2 · Also rejected: a machine-learning model¶

In plain words: I also trained three machine-learning models, each given all 32 inputs the rules could use. The best one was right only 46% of the time it raised an alarm. The simple two-clue rule was both more accurate and easier to explain.

The chart below scores the models exactly like the rules: same warning window, same 50 test machines.

Why a simple rule beats a 32-input model here:

  • The warning sign is very specific: a part's own sensor reads off while its own error code is logged. C09 looks for exactly that. A general model has to work out that pairing on its own, and the simplest model can't represent it at all.
  • The models catch nearly every failure (97–100%), but raise far more false alarms. One of them also leans on "hours since maintenance", the same misleading clue that sank C07.

Fair caveat: I didn't fine-tune the models, so this is a sanity check, not the best ML could do. My rule of thumb: an alarm people can understand and trust wins unless a model clearly beats it, and none did.

3 · Assumptions¶

Brief: a brief description of your assumptions.

  • The failure time in the log is accurate. Failures are logged once a day at 6 a.m., so I checked hour by hour that no after-the-fact data sneaks in before that time. None does.
  • The repair logged with a failure is part of the failure, not a warning sign. Otherwise "a repair was logged" would look like a perfect predictor.
  • Rules only use the past. At any hour, a rule can only look at readings from before that hour.
  • Machines never switch off (they always run), so there is no "idle" time to set aside.
  • The machines are similar enough that rules built on half of them carry over to the other half.
  • The false "fevers" are real behaviour of the machines, perhaps failures that a crew prevented. I didn't relabel them.

The fair test: training machines and test machines¶

I built every rule on 50 training machines (the dev set), then graded it once on 50 test machines (the holdout set) that never influenced any choice: not which ideas, not their settings, not the warning window. Every score in sections 1 and 2 comes from the test machines. A few edge hours aren't graded so nothing scores by accident: the failure hour itself (it holds the repair record), the day after a repair, and the first and last days of the year.

5.1 · How rules were ranked: one score, F1¶

What F1 is. Every alarm rule is judged on two questions:

  1. Of the breakdowns, how many did it warn about? (coverage, "caught")
  2. Of its alarms, how many were real? (precision, "real")

F1 rolls the two into one score from 0 to 1. Unlike a plain average, it is pulled down toward the weaker of the two. Think of a student who has to pass two exams: scoring 98 on one and 28 on the other doesn't average out to a pass. F1 is only high when both are high.

Why it's the right yardstick here. A plant manager needs both answers to be "most": most breakdowns caught, and most alarms worth walking over for. Each of the brief's three numbers can be gamed on its own:

  • Coverage alone rewards an alarm that's always on: it "catches" everything, but the crew soon ignores it.
  • Precision alone rewards firing only on the most obvious cases, missing most breakdowns.
  • Lift alone rewards a rule that almost never fires: one lucky alarm gives a huge lift.

F1 can't be gamed either way, so it's the one number used to rank all ten ideas and to choose the window. Lift is still checked (every kept rule clears the brief's bar of 2), just not used to rank.

The chart shows three of the ideas side by side:

  • C05 catches 98% of breakdowns, but only 28% of its alarms are real. A plain average would flatter it (63%); F1 gives it 0.44.
  • C06 is right more often (64%), but misses about half the breakdowns: 0.55.
  • C09 is high on both (99% caught, 90% real): 0.94.

5.2 · When an alarm counts: the 48-hour window (H and W)¶

In plain words: each part's sensor shifts about 48 hours before it breaks, in nearly every failure on every machine, so the window looks back 48 hours. An alarm in the last 12 hours is too late to do anything, so it only counts as a catch if it comes at least 12 hours ahead (H = 12). That leaves 36 hours in which an alarm counts (W = 36).

The timeline shows the window. The chart under it is where the 48 hours comes from.

When does an alarm count as a catch?

How to read this chart. Each line is one part's own sensor, averaged over every time that part failed and lined up so the failure is at 0 on the right.

  • The left-to-right axis is hours before the failure: a week ago on the left, the failure on the right.
  • The up-and-down axis is how far the sensor is from that machine's normal reading. 0 means normal. One step up or down equals one "typical wobble": how much that sensor normally bounces around on a good day (a standard deviation). So +2 means the reading sits about two typical wobbles above normal, and −1.5 means it has dropped well below normal (rotation slows down as a part fails).
  • One machine or all of them? All of them. Each line averages every failure of that part across all 100 machines (for example, all 252 rotation failures, spread over 92 machines). Averaging smooths out the hourly noise, which is why the lines look so clean. But it isn't just an average effect: when I checked failures one by one, 92–98% show the same clear jump, and the typical jump starts 47–48 hours before the failure for every part.
  • Why not plain units? The four sensors measure different things (volts, rpm, pressure, vibration). Measuring each one in "typical wobbles" puts them on one scale, so they can share a chart. It's like a body temperature: 98.6°F is normal and it wobbles by about half a degree, so 99.6°F is "two wobbles up", a real fever.

Why H = 12, W = 36¶

  • W = 36 covers the whole warning sign. Each part's sensor shifts 48 hours before it fails, and its error code lands 24 hours before. A window from 48 to 12 hours before the failure contains both.
  • H = 12 leaves half a day to act. With no buffer (H = 0), an alarm one hour before a failure would count as a catch, which leaves no time to do anything. Twelve hours is about one maintenance shift: enough for the crew on duty to diagnose, get the part and repair. Reliability practice sets the warning by the time needed to respond (the net P-F interval in reliability-centred maintenance; ISO 13381-1 bases alarm limits on maintenance lead time). For a real plant, H should come from its own repair and spare-part times.

What the two grids show:

  • A buffer of up to 12 hours costs almost nothing. H = 0 and H = 12 are within 0.01 on both grids (0.945 vs 0.936 on training machines, 0.947 vs 0.941 on test machines). So I took the 12 hours to act.
  • Waiting until 24 hours is too close to the edge. That's exactly when the error code lands. On the test machines the score drops to 0.84.
  • Past 24 hours, everything collapses. The window closes before the error code arrives, so C09 can't fire in time.
  • The two grids agree, so a choice made on training machines carries over to machines it never saw.

5.3 · What "normal operation" means¶

Normal hours are hours far from any breakdown: not in the 48 hours before one, not in the 24 hours after a breakdown or repair (the crew is at the machine and readings reflect the restart), and not in the first 24 hours of data (the averages need a day of history). Every threshold is set from normal hours only, as the brief requires.

5.4 · How abnormal counts as abnormal (thresholds)¶

In plain words: each machine is compared with its own normal readings, like comparing your temperature with your own normal rather than everyone's. A sensor counts as "off" once it's more than 3.09 typical wobbles from that normal. Random noise crosses that line only 1 hour in 1,000.

I didn't pick 3.09 by hand. Five lines were tried, from loose to strict, and C09 did best with this one (appendix A.3). Even the strictest line can't remove the false "fevers": they're real shifts, not noise. That's why the error code is needed.

It matches long-standing factory practice. Since 1935, British quality-control charts have used an "action limit" set so chance alone crosses it only 1 time in 1,000, which is exactly 3.09 typical wobbles (source). C09's tuning landed on the same line on its own.

6 · What I would do next¶

Brief: if you run out of time, what you'd do next.

  • Ask the plant about the false "fevers". If a crew fixed something before it broke, some "false alarms" were really saves.
  • Score in money. Once we know what a false alarm costs versus a missed failure, rank rules by money saved.
  • Test on real data. Here the warning signs land at exactly 48 and 24 hours. A real plant's history would show how much warning there really is, and set the window from that.
  • Cut repeat alarms. C09 often fires about twice per failure. Muting it for a day after the first alarm should roughly halve the noise.
  • Push the ML further: one model per part, and re-running the training/test split many times to check the choice is stable.

9 · Impact: what C09 gives you that you didn't have before¶

Before this analysis, a plant with this data could wait for breakdowns, alarm on sensors that cry wolf, or replace parts on a schedule. None of them works well:

Without C09

  • Breakdowns arrive as surprises
  • Sensor alarms: about 1 in 4 real, so crews tune them out
  • Replacing parts on a schedule: no real warning (C07)
  • An alarm says "something's off", not what
  • Black-box ML: right 46% of the time

With C09

  • 99% of breakdowns flagged ahead of time (346 of 350)
  • 9 in 10 alarms real; under 2 false alarms per machine per year
  • The alarm names which part is failing
  • One sentence anyone on the floor can check

What changes on the floor:

  • About a day of warning, so repairs can be planned. C09 fires about 24 hours before a failure, and only alarms at least 12 hours ahead count. That's a full shift to diagnose, get the part and fix it during a planned stop instead of an unplanned one.
  • Alarms worth answering. On the 50 test machines, C09 raised just 85 false alarms in a year, across all 50 machines, while warning about 346 breakdowns. A crew can afford to respond to every one.
  • It points at the part. Because C09 pairs each part's own sensor with its own error code, the alarm says which part (say, comp3, pressure), so the crew brings the right spare.
  • Nothing new to install. It uses the sensors and error log the plant already has.
  • Easy to trust. "This part's sensor has been off for hours, and its own fault code just fired" is something an operator can check on screen. There's no model to maintain or explain.

What it's worth depends on the plant's cost of an hour of downtime, which this data doesn't include. Once a plant shares that, the next step is to put a dollar figure on it (section 6). And since the data is simulated, real-world numbers will be lower. What carries over is the method: find each part's own sensor and fault code, pair them, and prove it on machines the rule has never seen.

Appendix A · Key terms and exact definitions¶

A.1 · Key terms¶

Term Meaning
Event a component failure. Failures on the same machine at the same hour count as one event (the brief's rule). "Any failure" is the main target; each part (comp1–comp4) is also run on its own.
Precursor / rule a pattern that tends to come before a failure, written as a simple yes/no rule checked every hour ("alarm" or "no alarm").
H and W for a failure at time T, the failure counts as caught if an alarm falls between T − (H + W) and T − H. Here H = 12, W = 36: an alarm between 48 and 12 hours before the failure.
Normal operation hours far from any failure: not in the 48 h before one, not in the 24 h after a failure or repair, and not in the first 24 h of data.
Lift how much more often a rule fires before failures than in normal operation (2 = twice as often).
Precision of the alarms a rule raises, the share followed by a failure within 48 hours (H + W).
Coverage of the failures, the share that had at least one alarm in their window.
F1 the single score used to pick rules: 2 × precision × coverage / (precision + coverage). It is high only when both are high, so it can't be gamed by never firing or always firing.
Training / test machines (dev / holdout) the 100 machines are split 50/50. The rules are built and tuned on the training (dev) machines and scored on the test (holdout) machines, which play no part in building them.
Drift a sensor moving away from that machine's own normal level and staying there, not just blipping. Like a person's temperature: one high reading is noise; running a fever all day is worth noticing. Each part's own sensor drifts in the two days before it fails.
Look-alike drift a drift that looks just like the ones before a failure, but no failure follows: the machine has an off day and settles back (~470 per part per year).

A.2 · The three rules, written out¶

Each rule is checked every hour on every machine, and raises an alarm when both of its conditions hold.

  • 6 h average: the mean of a sensor's last 6 hourly readings.
  • Typical wobble: how much a sensor normally bounces around on that machine (a standard deviation). Each machine is compared with its own normal (section 5.4 explains the 3.09 line).
  • Each part's own sensor and error code(s):
Part Sensor (direction of a fault) Own error code(s)
comp1 voltage (rises) error1
comp2 rotation (falls) error2 or error3
comp3 pressure (rises) error4
comp4 vibration (rises) error5

C09 · Matched signature (the alarm to act on). For any one part:

  1. its sensor's 6 h average is more than 3.09 typical wobbles away from that machine's normal, in the fault direction (on a typical machine: voltage above ~190 vs ~170 usually, rotation below ~383 vs ~449, pressure above ~113 vs ~100, vibration above ~47 vs ~40). 3.09 is the 1-in-1,000 line (section 5.4), and
  2. that part's own error code was logged at least once in the last 24 hours.

C08 · Drift + any error (the fallback):

  1. any of the four sensors' 6 h average is more than 3.72 typical wobbles away from that machine's normal, in its fault direction, and
  2. any error code was logged at least once in the last 48 hours.

C10 · Drift on an aging part (the early warning). For any one part:

  1. its sensor's 6 h average is more than 3.72 typical wobbles away from that machine's normal, in the fault direction, and
  2. the part has gone longer since its last replacement than usual: about 33 days for comp1, 31 for comp2, 34 for comp3 and 33 for comp4.

A.3 · The five sensor lines tried¶

Each idea was tried with five lines, from loose to strict (section 5.4):

How strict Typical wobbles from normal Random noise crosses it Normal hours that actually cross it Used by
loosest 1.64 1 hour in 20 6.8%
2.33 1 in 100 3.3%
2.58 1 in 200 2.8%
chosen 3.09 1 in 1,000 2.2% C09
strictest 3.72 1 in 10,000 1.7% C08, C10

How to read it. Going down, the line gets 500 times stricter for random noise, but the share of normal hours crossing it stops falling at about 2%. Those 2% aren't noise: they're the false "fevers", real shifts that no failure follows. So the sensor line alone can't be the alarm. That's the error code's job.

C.2 · Notebook 02: candidate precursors¶

Where the ten ideas come from. Before a failure, the dataset offers three kinds of evidence: four live sensors, an error-code log, and a maintenance log (from which I build each part's age). I listed the ideas in two rounds. First, what each kind of evidence could show by itself (C01–C07). These are the ideas anyone would write down before looking at the data. Then, combinations suggested by what notebook 01 found in the data and what the ML models in notebook 03 leaned on (C08–C10). Keeping the obvious ideas in the race shows whether the data-driven ones really add anything (section 2). This is step 3 of Oden's workflow, "generate hypotheses" (section 8).

Precursor vs. variant: what is being tested¶

A precursor is what to look for. A variant is how exactly it is measured.

  • The precursor (the idea) fixes which evidence is watched (a sensor, an error code, part age, or a combination) and what pattern counts as a warning ("this sensor goes abnormally high", "a sensor drifts and that part's error code appears"). Two different precursors make different claims about what comes before a failure.
  • A variant keeps the idea fixed and turns the knobs on how it is measured:
Knob The question it answers Choices tried
Smoothing Read the raw reading, or an average? hourly reading, held 3+ h, 6 h average, 24 h average, CUSUM
Usual level "Abnormal" compared with what? the whole fleet, machines of the same model, this machine's own history (plain or robust)
Cut-off How abnormal before it counts? from the top 5% to the top 0.01% of normal running
Look-back (error codes, part age) How recent or how old must the evidence be? error codes in the last 24 h or 48 h; part age above its P50, P75 or P90

So "vibration rises, 6 h average, compared with its own machine, top 1%" and "vibration rises, raw reading, compared with the fleet, top 5%" are the same claim measured two ways, and one may simply be the better measurement.

How every variant is tested (the same for all 655): set its alert line from normal-running hours only → run it every hour of 2015 on every machine → each off-to-on switch is an alert → score it on the 50 dev machines: precision (alerts followed by a failure within 48 h), coverage (failures with an alert 48 to 12 h before) and their F1. Holdout scores are recorded but never used to choose.

Why the comparison happens in two stages:

  1. Within each idea, its variants compete on dev F1 and only the best survives. That is tuning: each idea gets its best shot, so a good idea is never rejected for a bad setting.
  2. Between ideas, only those best versions compete, through the gates and the ranking (steps B5–B7 above). Comparing variant A of one idea with variant B of another directly would be unfair, because one could lose only because it had worse settings.

C.5 · Notebook 05: audit (trying to break the results)¶

Notebook 05 tries to break the shortlist with the classic traps. Each passes:

  • Luck from trying many ideas. 300 rules built from pure random noise, tuned exactly like the real ones, score about 0.08 at best, against C09's 0.94 (chart below). Picking the best of many tries manufactures almost no skill.
  • Leakage through the failure hour. Scoring the failure hour itself would turn "a repair was logged" into a fake perfect rule; the failure hour is never scored.
  • Counters that leak the future. "Hours since maintenance" looks excellent until it may only use past data, then collapses; the gate rejects it (C07).
  • Time drift. Rules set up on January–June alone still work on July–December (table below).
  • Different machines. C09 works on every machine model and age band (precision 0.87–0.93, coverage 0.97–0.99).
